## 1. Logic Chain System (NEW)

### What was built

A reasoning trace and backtracking memory system that prevents the bot from repeating failed approaches:

- **`core/logic_chain.py`** — Core module with:
  - `LogicChain`: persistent reasoning tree per problem (fingerprinted by query signature)
  - `ChainNode`: each step tracks approach, result, status (success/failure/partial/unknown)
  - `ChainMemory`: persists chains to `DriftMemory` via tagged concepts
  - `ChainNavigator`: main API for finding/creating chains, recording steps, avoiding repeats

- **Integration points:**
  - `core/brain.py` — `_generate()` stubbed in test; in production, `think()` and `agent_turn()` inject `[REASONING CHAIN]` blocks into prompts and auto-record approaches after generation
  - `interfaces/main.py` — chain navigator wired to `DriftMemory` for cross-session persistence
  - `INFJ_SYSTEM_PROMPT` — added `REASONING CHAIN` section instructing the model to never repeat failed approaches

- **`/chain` command:**
  - `/chain list` — show active in-session chains
  - `/chain show <id>` — inspect steps
  - `/chain mark <query> success|fail|partial` — mark last attempt
  - `/chain clear` — reset cache

- **Tests:** 25/25 passing

### How it works

When the user asks a question, the navigator:
1. Creates a stable fingerprint from the query (sorted unique words, hashed)
2. Checks if a chain exists for that fingerprint (in session cache or memory)
3. Injects a `[REASONING CHAIN]` block into the LLM prompt showing previously tried approaches
4. After generation, extracts the approach from the response and records it
5. If the user later marks it as failed/success, the chain updates and persists

### Key insight

The semantic overlap detection uses a 60% Jaccard similarity on 4+ character words. This catches variations like "check JWT expiry" vs "verify JWT expiration" without being so loose that unrelated approaches match.

### What actually changed

#### Condition D — Cosine-only RAG ✅ **Real difference detected**
- **Prompt length dropped by 326 chars (14.8%)** vs baseline
- This is because `retrieve_context_ranked()` normally applies DMU (Dynamic Memory Unit) re-ranking, which adds a second pass with time-decay + emotional-weight damping. The cosine-only stub skips this and returns raw semantic recall.
- **Implication:** The DMU re-ranking adds meaningful context to the prompt. Removing it reduces the memory context available to the model.

#### Conditions A, B, C — No measurable prompt difference ⚠️ **Stubs at wrong layer**
- Prompt length identical to baseline (2208 chars)
- The ablation stubs affected background/reflective methods (`elysium.reflect`, `shadow.background_tick`, `homeostasis.background_cycle`), but these are **not** the code paths that inject content into the assembled prompt.
- The prompt assembly happens in:
  1. `CognitiveOrchestrator.assemble_prompt()` — pulls being state, workspace, memory
  2. `CognitiveArchitecture.assemble_prompt_sections()` — registry-driven plugin output
  3. `get_being().format_being_prompt()` — formats being state
- **The stubs need to be placed at the prompt assembly layer, not the background cycle layer.**

#### Condition E — Local LLM only ⚠️ **No difference in prompt assembly**
- As expected, this condition only affects which LLM provider is used, not what goes into the prompt.
- In a real test with working providers, this would show latency differences (Ollama ~26-40s vs Gemini ~2-5s) and quality degradation.

## 3. Why Most Ablations Showed No Difference

### Root cause

The ablation suite stubs modules at their **background cycle** entry points, but the prompt assembly pipeline reads from **cached/stateful properties** that were already populated before the stub took effect:

- **Council (A):** `elysium.reflect()` is a background method. The prompt assembly doesn't call it directly — it reads from `COUNCIL_MAPPING` or workspace state that was already set up. Stubbing `reflect` only prevents future background reflections.
- **Shadow (B):** `shadow.background_tick()` updates the shadow radar. The prompt assembly reads `shadow.radar` which was already populated on module import.
- **Homeostasis (C):** `homeostasis.background_cycle()` updates needs over time. The prompt assembly reads `homeostasis.needs` which were initialized with default values before the stub.

### What would show differences

To make A, B, C show measurable differences, the stubs need to be placed at the **prompt assembly layer**:

```python
# A: No Council — clear council content from prompt
being.state.council_input = ""  # or similar prompt-facing property

# B: No Shadow — remove shadow radar from being prompt
shadow.radar = {}  # clear the data that format_being_prompt reads

# C: No Homeostasis — flatten needs in the prompt
for need in homeo.needs.values():
    need.current = 0.5  # must happen BEFORE assemble_prompt reads them
```

Alternatively, the ablation runner could monkey-patch `format_being_prompt()` or `assemble_prompt_sections()` to exclude the relevant subsystem's output.

## 4. What We Learned

1. **The DMU re-ranking adds ~14% more context to prompts.** This is non-trivial — it means the DMU is actively selecting and injecting additional memory beyond raw semantic recall.

2. **The prompt assembly pipeline is resilient to background module failures.** Even when council/shadow/homeostasis background cycles are disabled, the bot still assembles a full prompt from cached state. This is good for robustness but means ablation tests need to target the read path, not the update path.

3. **The logic chain system is fully operational.** It correctly fingerprints queries, persists chains, detects semantic overlap, and injects reasoning history into prompts.

4. **Provider outages make live ablation testing impractical.** With Gemini down and Ollama timing out, the only way to get timely results is with a stubbed LLM. The stub exercises the full prompt assembly pipeline but returns fixed responses, so response-quality metrics are not meaningful.
